## Findings

### Finding 1 (product): retained unreadable rows starve the drain window

STATUS 2026-11-14, same day: FIXED in src/sync.js (unreadable rows are now
quarantined on first sight, the same way cloud-rejected rows are dropped at
src/sync.js:326). Regression test: tests/sync-soak.test.js mixed-window case
plus tests/sync.test.js "an unreadable payload is quarantined on first sight
and never starves the window". The soak's known-bug classification was
removed again, so a post-fix soak run is strict.

Severity: HIGH for a corrupted-outbox scenario, MEDIUM overall (requires
payload corruption to start). Evidence: register-side log lines across run 5.

Where: src/sync.js. The drain reads the oldest 50 pending rows
(src/sync.js:263). A payload that JSON.parse rejects is skipped and retained
(src/sync.js:284: `unreadable++; unreadableIds.push(r.id); continue;`). The
only path that deletes unreadable rows is a window in which EVERY row is
unreadable (src/sync.js:288, `if (events.length === 0)`). In a mixed window
they are skipped every cycle, forever. The comment calls this "one wasted
slot, visible in the status"; measured reality is worse: the wasted slots
accumulate (about two per iteration in this soak, unbounded over time) until
the 50-slot window is majority skipped rows.

Measured: register process 23580 logged `sync: quarantined 0 cloud-rejected
and 37 unreadable outbox row(s)` on every drain cycle, 2.2 s apart, for its
whole life; consecutive processes show the retained count climbing 1, 3, 5,
8, 10, 13, 16, 19, 21, 23, 26, 28, 30, 33, 34, 36, 37 as iterations advance.
Productive capacity per cycle collapses from 50 rows to single digits, and
chunk iterations pushing 130+ rows exceed any reasonable settle bound
(iterations 32 and 33 failed exactly this way: pendingReadable 76 and 39).

Failing assertion (quoted): `iteration ${i} drain never settled
(pendingReadable ${pendingReadable}, command acked ${acked})`, thrown by the
settle poll bound in tests/sync-soak.test.js after DRAIN_TIMEOUT_MS (45 s).

Remediation suggestion (NOT applied, tests-only pass): quarantine unreadable
rows on first skip, the same way cloud-rejected rows are dropped on
src/sync.js:326. A payload that cannot be parsed is not self-healing; the
current drop path (whole-window-unreadable) rarely fires because a handful of
retained rows keep every window mixed. Alternative: drop after N consecutive
skipped windows, or log the retained ids so an operator can see the queue
starving. The status endpoint already surfaces pending_rows; add an
unreadable marker there.

### Finding 2 (product, open): iteration 25 stalled with two readable rows and no backoff evidence

STATUS 2026-11-14, same day: still open. With Finding 1 fixed, the soak is
strict again, so if this stall recurs the run fails loudly and the error
names the stuck rows (id, table, local_id, payload length) plus the
retained-unreadable count.

Severity: MEDIUM (unexplained). Iteration 25 pushed only 22 rows, killed at
2680 ms, restarted, and two parseable rows never settled within 45 s
(pendingReadable 2, command acked true). Throughput collapse (Finding 1) does
not explain two stuck rows at that backlog depth, and the register logs show
zero `sync: push failed` lines in the entire run window, so no 400, no
backoff, no cloud outage was involved. The stuck rows' identities were not
captured in run 5. The harness now names them in the stall error
(retainedUnreadable count plus up to 10 stuck rows with id, table, local_id,
payload length), so the next deliberate soak run pins them. Deferred under
the stop condition; the defect cannot be classified further this run.

### Finding 3 (harness): the settle bound under-provisions chunk iterations

Severity: LOW, harness calibration. The 45 s settle bound assumes near-empty
windows; under Finding 1 starvation a 130-row chunk iteration cannot drain in
time. Once Finding 1 is fixed, re-measure and adjust DRAIN_TIMEOUT_MS or the
mix sizes.

## Contract checks that held (47 clean iterations, run 5)

- No loss: every valid enqueued row appeared on the mirror with exact content
  (deepStrictEqual per key) in every settled iteration.
- No duplication: the mirror held exactly the expected key set; every crafted
  key existed once; replays upserted onto the same mirror key with identical
  content.
- Acked-only marking: every readable outbox row ended synced or dropped,
  per row, per documented contract; no readable row ever stayed queued at
  settle time on a clean iteration.
- Rejected rows: cloud-rejected rows were dropped from the outbox exactly
  once and never retried; register-side tables were never touched.
- Unreadable rows: dropped only when their whole window was corrupt,
  retained otherwise, matching the documented (and, per Finding 1, harmful)
  behavior.
- Commands: exactly-once apply under kills, dedupe at issue (deduplicated:
  true) and at apply (op_log), floor refusal impossible in this harness.
- Heartbeat: last_seen truthful through 50 restarts.
