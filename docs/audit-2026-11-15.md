   that changes the cost silently keeps the old cost, wrong margins on register and cloud.

   already-applied row: the UI's own recovery advice silently inflates stock.

   per keystroke: the mission's main field-PC lag finding, visible from about 1000 rows on the

#1 [HIGH] [CONFIRMED] src/inventory.js:645-658 with :216-219 - Supplier receive never reprices unit cost on the real UI path
What: receiveInventory builds meta.op_id = line.op_id + ':' + item.id and passes the same meta
to adjustStock (which records it in op_log) and then to updateInventoryItem for the cost
reprice. updateInventoryItem's double-submit dedup sees the op_id adjustStock just wrote and
returns early, so cost_price never changes while the response and toast still report the new
unit cost. Orchestrator-verified by direct read.
Trigger: Receive-from-reorder on the dashboard (public/js/views/backoffice.js:1490 always sends
per-line op_id) with a unit cost entered.
Impact: every received part whose cost changed keeps the stale cost: wrong margins, wrong
reorder est_cost, wrong valuation on register and cloud mirror. Silent.
Impact-class: FIELD-NOTICE
Fix sketch: pass a meta without op_id (or a distinct suffix) to the reprice call; add a
regression test that sends op_id together with unit_cost (tests/reorder.test.js:381 omits
op_id, which is why it misses this).

## 3. Future Scale Notes (10-100x volume)

- The inventory table (unpaginated) becomes the app's worst interaction at 2000+ rows; the
  server already accepts limit/offset, so the fix is client-side only (#20).
- namefold() predicates defeat the customer indexes (function-wrapped columns); listCustomers
  runs three full-scan aggregates per request; getCustomerDetails returns multi-MB payloads
  before its parameter ceiling (#22). All three want pagination or denormalized debtor totals.
- listSales search is five LIKE %term% alternatives, a full scan per keystroke; an index
  strategy question at scale.
- GET /api/inventory never passes the limit/offset listInventory supports; the POS fetches the
  whole catalog each load; fine to 2000 rows on this hardware, blocky at 20k.
- repriceCartLines rebuilds a catalog Map per cart mutation; trivial at 2k rows, wasteful at 20k.
- Cloud analytics run json_extract full mirror scans per request with no request budget on
  authenticated manager routes; materialize typed tables or add a budget at 10x.
- Shop zones that observe DST would drift a fixed SHOP_TZ_OFFSET_MINUTES one hour twice a year;
  the Philippines is unaffected.
- The dashboard reorder rail (1 day), counter reorder sheet (3 days) and phone reorder sheet
  (7 days) use the same formulas over different default windows; each surface self-consistent,
  the defaults disagree.
- Import delta semantics will collide with operators who think in absolute shelf counts even
  without the partial-apply path; document or switch semantics before scale amplifies it (#2).
- License enforcement stays cloneable while the machine binding is a settings row (#24); the
  vendor's two-PC support load grows with every copy-paste tutorial.
- The audit log's Load-more accumulates DOM without a cap; fine for years at one shop.
- Spawn-per-slip at 10x volume is 17-40 minutes of aggregate PowerShell startup per day; a
  persistent helper would cut it 5-10x but is not warranted at this scale.
- startServer's stale-binding pattern is a class: any future feature that destructures
  createServer's db at start time will repeat #14. Prefer threading getDb everywhere.
- A restore on a paired shop leaves the cloud holding post-snapshot rows the restored register
  no longer has; acceptable while the cloud is disposable, a real reconciliation problem at
  multi-register scale.
- Get-GithubReleases reads page 1 only; past 100 releases the duplicate check can miss the
  newest page.
- If the shop ever runs two seats printing concurrently, the spawn cost becomes visible;
  configured shops skip the enumeration.
- The soak's 50 iterations scale linearly; a 10x counter would want a configurable ITERATIONS.
