## Findings

### 1. MEDIUM, CONFIRMED: cloud-command poison loop survives one error shape
`src/sync.js:102` (`COMMAND_REFUSED`) classifies deterministic cloud-command
failures by message sniffing: `/not found|must be|insufficient|too small|UNIQUE
constraint|required/i`. A malformed command that instead trips a database
constraint, for example `NOT NULL constraint failed: inventory.sku` or
`FOREIGN KEY constraint failed` (an import_inventory row with a missing required
column that validation does not name), matches none of the alternatives, stays
un-acked, and is retried on every drain forever. That is the exact poison-retry
loop the c8a2751 fix set out to kill; one shape of the same bug survives.
Trigger: cloud manager sends a command whose payload the register rejects at the
SQL layer with a constraint error. Consequence: the command is served on every
sync tick indefinitely and the drain log fills with "failed, will retry".
Fix sketch: extend the refused classifier with `constraint failed` (covers NOT
NULL, FOREIGN KEY, CHECK and UNIQUE in one alternative), keep everything else
retrying.

### 2. LOW, CONFIRMED: boot_at staleness guard assumes the wall clock stands still
`src/server.js:1982` (`isInstanceLockLive`, landed in cf06069) judges a lock
stale when `Math.abs(bootAt - existing.boot_at) > 60000`, where `bootAt` is
recomputed from the current wall clock each call (`currentBootEpochMs`, :1952).
A system clock step larger than 60 seconds while a server is running (manual
time change, a large NTP correction) makes a LIVE lock read as stale: the next
launcher or direct start unlinks it (:2281) and boots a second instance, which
drifts to another port and runs a second watchdog and backup ticker against the
same shop.db. WAL keeps the data safe; the counter sees two servers. Rare, and
the cheap fix is documentation, not behavior: the honest alternative (probe the
locked port before declaring stale) needs async in a sync path.
Fix sketch: a comment naming the ceiling at the guard, no behavior change.
