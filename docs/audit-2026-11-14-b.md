## 2. Findings by category

### Category 1: correctness

[FINDING 1] [MEDIUM] [CONFIRMED] src/inventory.js:436-447 with
src/inventory.js:257-292 - step-execution failure still aborts the whole
import with a non-row error.
What: the partial-import change moved per-row problems into result.errors,
but the per-row try/catch only guards step CONSTRUCTION. Step EXECUTION runs
inside the transaction at the return block, and one cause still throws there:
a matched row whose negative stock_quantity exceeds the part's current stock
hits adjustStock's floor refusal ("Insufficient stock: cannot reduce stock
below 0", src/inventory.js:292, the atomic guarded UPDATE misses and throws).
A second candidate cause, a matched row reassigning its sku_barcode onto
another part, is STRUCTURALLY UNREACHABLE: the match logic consults bySku
before the brand/model/type triple, so a row carrying a foreign SKU matches
the holder itself and updates it harmlessly.
Trigger: import a sheet that reduces one part by more than it holds.
Impact: the whole import rolls back and the route answers a 400 whose message
is neither row-numbered nor actionable, breaking the contract just shipped to
the client; data is safe (rollback) but the promise "good rows land, bad rows
are stated" fails for this cause.
Fix sketch: in the row loop, for matched rows, pre-validate the floor (the
matched row's current stock plus the parsed qty stays at or above zero),
turning it into a normal "Row N:" error before any step is built.

[FINDING 2] [MEDIUM] [CONFIRMED] src/sync.js:306 with cloud/server.js:501 -
a whole-batch-400 wedge survives for windows of only-cloud-invalid rows.
What: the 2026-11-14 quarantine fix removes unreadable payloads on first
sight, which was the measured starvation mechanism. A drain window whose
readable rows are ALL rejected by the cloud (50 consecutive constraint
violations) still gets the cloud's whole-batch 400 (validated.length === 0
and rejected.length, cloud/server.js:501), the shop throws on any non-200
(src/sync.js:306) without reading the rejected array the 400 body carries,
and the same window repeats behind backoff forever.
Trigger: a workstation bug or schema drift enqueues 50+ rows the current
cloud refuses; every drain retries the identical head window.
Impact: every newer row starves behind the wedge until manual surgery on the
outbox; rarer than the fixed starvation but same shape.
Fix sketch: on a 400 whose body carries a rejected array, quarantine the
listed outbox ids (drop, count, log) before throwing; the cloud already
provides the list.
