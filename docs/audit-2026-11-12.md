## 2. Findings by category

### Category 1: Correctness / bugs

[MEDIUM] [CONFIRMED] public/js/views/pos.js:1145 - Fractional line display disagrees with
the register total.
What: renderOrderLines computes each line's displayed amount as
Math.round(toCents(unit) * qty), while cartTotals (pos.js:1247) and the claim stub
(receipts.js:986) were both changed to round the unit times qty PRODUCT to cents, matching
src/money.js. The two formulas differ on decimal-half products.
Trigger: sell a fractional-qty line whose unit times qty lands on a half-centavo, for
example unit 12.35, qty 0.3: toCents(3.705) floors the float artifact to 370 (3.70, which
is what the server charges), while Math.round(1235 * 0.3) gives 371 (3.71).
Impact: the order-line amount on the counter screen can read one centavo above the
subtotal the cashier collects and the register charges; a cashier reconciling the drawer
sees a phantom difference.
Fix sketch: compute lineCents with the same product-rounding cartTotals uses
(toCents(unit * qty)), or factor one helper both call.

[LOW] [CONFIRMED] src/inventory.js:122 (validateInventory) - allow_fractional flag parsing
inconsistent with the CSV path.
What: validateInventory reads Number(data.allow_fractional) truthiness, which accepts 1, 0,
true and false but rejects the strings "true"/"yes"; importInventory's CSV path uses
parseBoolFlag (inventory.js:79), which accepts them.
Trigger: a non-browser client (or a hand-built API call) posting allow_fractional: "true"
gets 0 while the same CSV value gets 1.
Impact: two entry points disagree on one flag; confusing, not corrupting.
Fix sketch: route validateInventory's flag through parseBoolFlag too.

[LOW] [CONFIRMED] src/printer.js:647 - fractional quantities print as "0.5x".
What: slip item rows render qty followed by a literal "x".
Trigger: any sale with allow_fractional stock, for example 0.5 kg.
Impact: cosmetic oddity on paper ("0.5x P60.00"); readable, no math impact.
Fix sketch: print the qty without the "x" suffix when it is not an integer, or use the
item's uom.

[POSITIVE, verified] src/settings.js:30-62 - the four numeric setting readers now treat an
empty stored value as NaN and fall back to the default. Before this batch, an empty
settle_elevation_threshold row yielded Number('') = 0, which silently disabled the
settlement elevation gate. This is fixed; no finding.

### Category 2: Concurrency and data integrity

[HIGH] [CONFIRMED] src/sync.js:101-135 (applyCloudCommands) with cloud/server.js:1547 -
cloud stock commands that fail deterministically on the workstation enter a silent
infinite retry, and the manager cannot see it.
What: applyCloudCommands acks a failed command only when its error message matches
/not found|must be/i, and records nothing otherwise. Two realistic failures match neither:
adjustStock throws "Insufficient stock: cannot reduce stock below 0 (...)"
(src/inventory.js:285) when the guarded update refuses, and a stale-mirror cloud import can
hit "UNIQUE constraint failed: inventory.sku_barcode" when the shop already created that
SKU after the mirror last synced. A command in that state is neither acked nor quarantined,
so cloud/server.js serves it again on every /sync exchange, applyCloudCommands throws again,
every drain, forever, with no log line anywhere. Meanwhile the cloud's adjust-stock route
already mutated its own mirror with a clamped Math.max(0, ...) result (cloud/server.js:1547),
so the manager's phone shows the new stock as if applied.
Trigger: manager receives stock on the phone while the counter sold below the expected
level, or a CSV import uploads a SKU the shop created first.
Impact: a permanently poisoned pending command plus a permanent mirror-versus-register
divergence, both invisible. This is the worst failure mode the sync design itself names
(rows that silently never reach the shop, or numbers that silently disagree).
Fix sketch: two halves. Workstation: ack any deterministic failure (not found, validation,
insufficient stock, UNIQUE violation) so redelivery only happens for transient errors, and
logLine every swallowed error. Cloud: apply the same floor rule against the mirror at
request time and answer 409 instead of clamping, so the manager sees the refusal the moment
they make it.

[POSITIVE, verified] The setup-pin shop-adoption steal is fixed: setup-pin now adopts only
shops with store_id NULL or empty (cloud/server.js:606-609), and the comment documents the
old clause's cross-tenant grab. A new global pair budget (PAIR_GLOBAL_BUDGET_LIMIT 120/min
at cloud/server.js:385-393) backs the spoofable per-client budget, closing the distributed
crawl the v9 brief asked to measure. Both confirmed in code and covered by tests.

[CLEAN otherwise] op_id dedup holds across the new cloud commands (cmd.op_id or
cloud-cmd-<id> rides meta, so a redelivered command replays as a no-op via op_log);
adjustStock keeps the atomic guarded UPDATE (inventory.js:296-303); the import mirror-sum
matches importInventory's add semantics; shop deletion now clears cloud_commands with
shop_rows (cloud/server.js:921).

### Category 4: Security

[HIGH] [SUSPECTED runtime outcome; script order CONFIRMED] installer/TechPartsPOS.iss:51-56,
:71-72 - pre-created data subdirs keep ProgramData's default ACLs; Users can read shop.db.
What: [Dirs] creates TechPartsPOS, data, backups, updates and runtime during the install,
and [Run] then grants the root only SYSTEM Full with /inheritance:r. icacls applies an
inherited (OI)(CI) ACE only to children created afterwards; children created BEFORE keep the
ACEs they inherited at creation (ProgramData defaults: Users Read+Execute, Administrators
and SYSTEM Full). Only runtime is re-granted explicitly (:72). data and backups therefore
inherit Users Read+Execute, and shop.db and every snapshot created by the SYSTEM service
inside them inherit from those dirs.
Trigger: install on any machine, log in as the standard cashier account, read or copy
C:\ProgramData\TechPartsPOS\data\shop.db.
Impact: README.md:34-35 promises cashiers "cannot view, copy, modify, or delete" the
database. Read and copy are the leak: the full ledger, customer list, and the PBKDF2
manager PIN hash (a 4-digit space, crackable offline in seconds at 100k iterations) all
leave the machine on a USB drive. Modify and delete are still blocked (no write or delete
ACE for Users), so tampering prevention holds but confidentiality does not.
Fix sketch: grant the three subdirs explicitly the way runtime already is, or run the root
grant with /T so it walks existing children, then re-grant runtime its Users read. Verify
on a real installed machine (Measurement List item 1).

[MEDIUM] [CONFIRMED] installer/TechPartsPOS.iss:93 - DeveloperToolsAvailability=2 allows
DevTools in the kiosk browser.
What: the installer writes the Edge policy allowing Developer Tools (value 2) while the
app's kiosk lockdown (public/js/main.js:668) blocks F12 and the Ctrl+Shift+I/J/C chord
in-page.
Trigger: any seat opens the browser menu and picks a DevTools entry the page cannot block.
Impact: the lockdown's purpose (a cashier cannot poke at the register's internals) is
defeated by a policy the installer itself writes; a staff seat can read its own session
token, network tab, and console.
Fix sketch: write 0 (never allow) for this kiosk machine instead of 2.

[MEDIUM] [CONFIRMED] docs/API_REFERENCE.md - Appendix A completeness claim contradicts the
disclaimer and omits 6 routes.
What: the header says the reference "is not an exhaustive enumeration" and names the
update-check/progress routes as the example gap; Appendix A then claims to be "the
complete route index: every pattern src/server.js matches". An awk cross-check of the 51
unique literal pathname matches in src/server.js against the document shows 6 absent:
/api/auth/recovery-status, /api/auth/recovery-password, /api/auth/recover-pin,
/api/backup/download, /api/receipt/preview, /api/inventory/reorder. The update routes the
disclaimer names ARE documented, so the disclaimer's example is stale on both ends.
Trigger: a developer or integrator trusts Appendix A and builds against a route that is
not there (or trusts the disclaimer and misses one that is).
Impact: the docs are the spec by this project's own convention; a wrong completeness claim
on an auth-bearing route set (recovery) is worse than a missing page.
Fix sketch: add the 6 rows to Appendix A with their gates, and rewrite the header
disclaimer to match what the appendix actually covers.

[LOW] [CONFIRMED] src/server.js:1370 - backup download Content-Disposition accepts names
that can carry quotes.
What: the name is validated against /^(shop-|shop_backup_).*\.db$/ and a basename check,
which blocks traversal but permits quotes and other characters inside the middle .*
segment; the header interpolates it unescaped.
Trigger: requires a file with a hostile name to exist in the backup directory, which only
local file access or a restore of such a file can create.
Impact: header syntax breakage at most; no traversal, no injection into a command line.
Fix sketch: restrict the middle segment to [A-Za-z0-9._-] in the shared
resolveVerifiedBackup regex.

[POSITIVE, verified] The login route now issues a factory-PIN session WITHOUT elevation and
answers pin_change_required (src/server.js:1524-1531), so a LAN peer who logs in with 1234
walks past nothing; the three recovery routes sit exactly where the brief's posture wants
them (recovery-status and recover-pin on both exempt lists, recovery-password gated on an
elevated non-default staff-free session, src/server.js:456-457, :1583-1619); recovery has
its own 15-minute lockout namespace (src/auth.js:90-93); PRIVATE_SETTINGS carries the three
new recovery keys (src/settings.js:5-9); the three cloud console prints the v9 brief
listed as STILL OPEN now point at credential FILES instead of printing tokens
(cloud/server.js:142, :157, :217; verified no fourth leaks a secret); SSE clients are
store-tagged at /events (cloud/server.js:1797) and broadcast() filters by store
(cloud/server.js:272-277), closing the multi-shop scope leak; /api/pair never logs its

## 3. Future Scale Notes

- The cloud command channel is the seed of a real write API: if more kinds arrive, the
  workstation needs one dispatch table with a failure taxonomy per kind, not a regex.
- mirror-backups and any backup mirror will happily copy publish/ (2.2 GB); a scale-up or
  a second shop multiplies that cost.
- The datetime() wraps in reorder queries will matter at 100x sales volume; an index on
  date(created_at) or a precomputed day column is the upgrade path.
- Three implementations of profit and freshness (workstation, cloud, phone) become a
  contract question, not a convenience, the day a second cloud consumer appears.
