  What: The dirty CHANGELOG/RELEASE_NOTES replace the published v2.6 highlights ("EACCES port drift", "ergonomics", "in-stock filter pill") with three different claims ("sale retries retain one operation id and validate credit downpayments", "settings save leaves write-only sync token unchanged when blank", "report authentication is scoped to session storage").   Trigger: Next person diffs the tree, trusts the changelog, or a future publish script drafts release notes from the wrong content.
  Impact: Documentation integrity; the released v2.6 no longer matches the repo's own release notes.
  Fix sketch: Restore both files from HEAD (8103023), which matches what was actually published.

- [MEDIUM] [CONFIRMED] src/updater.js:436-451 - :restore branch can fail its rename silently and still log success
  What: The restore branch deletes the target then renames .old back, with no errorlevel check after either step. If the partial target cannot be deleted (locked, antivirus scan), ren fails and the next start launches the partial exe; the handoff log already said "copy FAILED; previous exe restored", so the operator is told a restore happened that did not.
  Trigger: A failed copy leaves a locked or partial target file and :restore runs.
  Impact: A rare but unrecoverable-looking update failure at the counter; misleading handoff evidence.
  Fix sketch: Add `if errorlevel 1` logging after the ren (and after the del), appending a "restore FAILED" line so the next boot prints the truth.

- [LOW] [CONFIRMED] src/updater.js:581-598 - staged-reuse path deletes retry material when the digest fetch merely fails
  What: If fetchPublishedDigest throws on a transient network error inside the staged-reuse branch, the catch swallows it and the code deletes the staged exe and marker, forcing a full re-download next attempt. Fail-closed, but it destroys exactly the material the feature exists to reuse.
  Trigger: Update Now clicked twice across a flaky connection with a leftover staged exe.
  Impact: Wasted bandwidth and a longer counter outage; no integrity risk.
  Fix sketch: Only clean the staged pair when the digest fetch SUCCEEDS and mismatches, or when the marker/url is invalid; on a fetch error, keep both and throw the verify error.

- [LOW] [CONFIRMED] src/server.js:1952 - port retry bound tightened from +21 to +20 without a doc note
  What: The v2.6 EACCES change also changed the retry condition from `currentPort <= preferredPort + 20` to `currentPort < preferredPort + 20`, so the last attempted port is +20, not +21. Harmless, but OPERATIONS_AND_DEPLOYMENT.md still describes the old bound.
  Trigger: Reading the docs and counting ports.
  Impact: One fewer fallback port than documented.
  Fix sketch: One doc line, or restore `<=`.

### Category 7: Observability and operations

- [MEDIUM] [CONFIRMED] src/server.js:942-990 - a 15 s pairing abort after the cloud spent the code strands the shop identity
  What: POST /api/settings/pair-cloud aborts at 15 s. The cloud mints the shop, persists the credential, spends the code, and only then responds. If the response is lost to that abort, the workstation saved nothing while the cloud holds a paired shop bound to the register's stable UUID. Every retry with a new code answers 409 ("already paired; rotate on the server"), so recovery requires vendor-side credential rotation.
  Trigger: Slow link or VPS stall during the pair handshake.
  Impact: The operator sees "Connecting..." then a 502 with no hint that the cloud side completed; pushes to the cloud never authenticate; a vendor hand-off is needed to recover.
  Fix sketch: Catch the abort and return a message that names the state (the cloud may have completed the pairing; pushes will 401; the vendor can rotate the credential), and say the same in OPERATIONS_AND_DEPLOYMENT.md.

- CONFIRMED RESOLVED: the updater now logs ~20 updateLog call sites into pos-server.log (check results, apply refusals with reasons, staged reuse, handoff milestones), the audit row for update_apply carries version and URL, and the quarantined-row counter logs one line per drain with rejections. The release pipeline keeps a draft release until every asset is uploaded, so a failed publish no longer strands a tag pointing at a partial published release (verified by reading scripts/publish-release.ps1:463-500).
